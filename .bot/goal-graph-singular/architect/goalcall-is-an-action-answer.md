## Q2 — not `app.Run`; the held node runs itself, and runtime arguments are variables

`app.Run(action, context)` is the seam for actions COMPOSED IN C# — it births an entity with `Step = context.CallStack.Current?.Action.Step`. A held goal.call is a graph node born in the `.pr` with its step. It runs itself: `await held.Run(context)` (`action/this.cs:159`), the same door `Action.Recovery.Run(context)` uses (`error/handle.cs:97`).

What the plain dispatch does NOT give is the runtime arguments. Today every callback site builds a THROWAWAY `GoalCall` per invocation (`OpenAi.cs:538-549`: `Name`/`PrPath` copied off the held call, runtime rows `name`/`arguments`/`status` added — and the held call's own authored arguments are silently dropped). Under A the node is program structure and is never stamped per invocation. Runtime arguments are run-state: the callback sets them as variables in the context it runs under (`context.Variable.Set(name, data)` — the very door `RunGoalAsync:554-563` uses for authored arguments), then runs the held node; the node's `Run` binds its authored arguments after that, so an authored name wins a collision (today the authored ones were lost — this is a fix). Each callback's contract — which variables it provides (`%name%`, `%arguments%`, `%status%` for `OnToolCall`; the `TransferProgress` fields for `OnProgress`) — goes in that action's teaching notes: it is the callee goal's interface. `call.Actor` (`call.cs:19`) still picks the context the goal runs under.

## INGI'S ANSWERS (same day, via coder) — Q1 overruled, Q2 asked back, Q3/Q4 settled

- **Q1 — `Parallel` is a bool on the `call` class, like `Actor`** (Ingi). Accepted; my `llm.query` placement is withdrawn. The reasoning that makes his placement right: "safe to run beside others" is a fact about the CALL (the callee's nature), and the runner owns the policy — degree of concurrency, caps, provider limits. Today's runner (`OpenAi.cs:347-352`) is all-or-nothing; that stays the runner's business.
- **Q3 — `Name`.** Settled. **Q4 — order approved.**
- **Q2 — Ingi: "plain `app.Run`, probably — not sure why not. Say so if you see a reason it can't."** There is one, and it is in the two bodies:

`app.Run<TAction>(handler, context)` (`app/this.cs:449-467`) takes a HANDLER — a C#-composed `ICodeGenerated` whose parameters are already set as properties — and makes a node for it: `new action.@this { Module = …, Name = …, Seed = handler, Step = context.CallStack.Current?.Action.Step }`, then `entity.Run(context)`. Its own doc says what it is for: "used by C# composing actions (providers, tests)", and that it "may be removed entirely when handlers grow their own RunAsync surface" (`:445-447`). So `app.Run` = **make a node for a handler that has none, then run the node.**

A held goal.call already IS a node: born in the `.pr` with its own `Step`, its own `Parameter` rows, its own `Modifier` list (an authored `on error` / `cache` / `timeout` on the call) and its own `Recovery`. `node.Run(context)` (`action/this.cs:159-199`) pushes the frame with THIS node, runs the lifecycle `Before` keyed on it, folds ITS modifiers, then dispatches — minting the handler from the module and binding the parameters lazily. Running the held call through `app.Run` instead would mean: (1) the caller mints the handler first (`node.Instance(context)`) — the module's job done by the callback; (2) `app.Run` births a SECOND entity for the same call, with `Step` = the callback's frame (not the node's birth step) and with NO modifiers — an `OnProgress=call Report, on error ignore` silently loses its `on error`; (3) the frame on the call stack is the throwaway entity, so `%!error%`, the audit and any snapshot point at a node that is not in the program. That is why it can't: **`app.Run` composes a node; the held call has one; composing a second drops the call's modifiers and mis-parents its frame.**

Not two ways for one operation — two operations: "make a node for a handler" (`app.Run`, C# composition, scheduled to shrink) and "run a node" (`node.Run(context)`, what `Action.Recovery.Run`, `step.Run` and `goal.Run` already are). Callbacks do the second. Runtime arguments as variables before the run, as ruled above.

## FOR INGI — two points he disagreed with or asked about (put to him in the architect session, 2026-09-23)

**1. `PrPath` — Ingi: "a straight link to the pr files that should run, which should give us faster execution."** My position, from the code: the stamped path is today the SLOW door, not the fast one. `GoalCall.GetGoalAsync:174-176` treats `PrPath` as authoritative and goes straight to `LoadFromFile` (`:263-320`), which reads and parses the `.pr` from disk on EVERY call and never registers the goal (no `Add`). A `foreach` calling a goal a thousand times pays a thousand reads and parses. The fast door already exists and is the collection: `goal.list.Get(name)` (`:67-77`) is a dictionary hit; `GetAsync(name, callingFolderPath)` (`:123-162`) tries the cache, then loads relative to the caller, then root-relative, and `LoadFromFileAsync` registers what it loads (`:373 Add(primary)`), so every call after the first is a dictionary hit. What a stamp saves is only the failed probes on the FIRST resolution (one or two existence checks), microseconds once; what it costs is a second truth beside the name that goes stale when a folder is renamed or a `.build` moves, and it cannot cover `call %goalName%`, so the by-name search must exist anyway — two paths for one operation. **Recommendation:** no stamp; the caller-chain walk folds into `GetAsync` and the handler asks the collection. **If Ingi still wants a build-time link:** stamp the goal's canonical NAME (app-absolute, e.g. `/system/builder/EmitBuildEvent`), not a file path — the identity is settled at build, robust to layout, and still one dictionary key at run; and any path hint the builder writes is a lookup key the COLLECTION uses (`app.Goal[path]`, cached), never a bypass of the cache. `ResolveGoalCallPaths` then either dies (no stamp) or stamps the canonical name (construction, as today); the name repair is independent and becomes a `SetValue` on the `Name` row. Measurement, if wanted: coder times 1000 calls to one goal both ways on this branch — no build here to run it myself.

**2. `Parallel` as a class — Ingi: "the runner could then just enable it and it would run with some default settings that we decide, or he could fine tune it; we could then also have multiple properties."** What a call-level `parallel` value can honestly hold: `Enabled` (this call may run beside its siblings) and `Max` (at most N instances of THIS call at once — a fact about the callee, expressible at the call site). What it cannot: the degree and ordering of a BATCH — those belong to the runner that has the batch (the tool loop, a parallel foreach), and putting them on every call site stores one policy n times. OBP shape if he wants the class: a `parallel` value type under the call (`goal/call/parallel/this.cs`, `[PlangType("parallel")]`, `Enabled` + `Max` with `[Default]`s so a bare `parallel` enables with our defaults), the runner reads the value and applies its own batch policy on top. **Recommendation:** the bool now, the class the day the second property has a caller — unless he already knows the second property is per-call `Max`, in which case the class is right from day one and the runner's batch settings stay the runner's. The one question that decides it: which second property does he have in mind — a cap on this call, or the batch's degree/order?

## DECIDED with Ingi, live (2026-09-23)

- **`Parallel` stays a bool on the call.** The batch run object (one `parallel` object replacing the three hand-rolled loops: OpenAi tools, `test.run`'s semaphore, a future parallel foreach) is PARKED — "takes our focus off the ball". Not built on this branch; logged here for later.
- **`PrPath` dies; determinism comes from the canonical NAME.** Ingi: "want is determinism — that is it." The build writes the goal's canonical, app-absolute name into the call's own `Name` slot (e.g. `/system/builder/EmitBuildEvent`): one truth, one slot, a dictionary hit at run, and a later-added same-named sibling cannot retarget a built caller. A bare child name (`call Compile` inside the same file) stays bare — the child wins by rule and cannot be shadowed; a `%var%` name stays authored. The goal answers its own canonical name (one NEW one-word member on `goal`; `FullPath` at `goal/this.cs:194` is a file path, not the identity — coder names it).
- **`ResolveGoalCallPaths` is an obpv (Ingi) and dies:** the canonicalization is the `call` handler's OWN `Build()` (`call.cs:27`), the compile-time hook the build pass already runs on every bound handler (where `Validate()` now sits beside it). The handler rewrites its own `Name` row through the collection's resolution (`goal.list.GetAsync(name, callerFolder)`) from its own step's goal.
- **The build pass becomes node-owned — Ingi: "the key in OBP is: walk becomes node-owned."** `RunBuildPass` (`Default.cs:359-386`) walks only the step's top-level actions — no `Modifier`, no `Recovery` — which is why `ResolveGoalCallPaths` hand-walked modifiers beside it. Ruled and approved: `action.Build(context)` mints and resolves its handler, runs the handler's `Validate()` + `Build()`, and recurses into `Modifier`, `Recovery`, `Child`, and every parameter whose DECLARED type is `action` / `list<action>`; `action.list.Build` iterates; the builder calls it and reacts. The walker dies into it — the same shape Stage D gave `Validate`. Goes in A1 (the canonicalization depends on the walk reaching a call inside `on error`); coder may split the commit.
- **A2 check that follows from the same point:** a parameter-held action (a `Data<action>` slot) is READ by the holding action's reader, the way it reads `recovery` and `child`, keyed on the row's declared type — the action reader is born with its step, so the registry cannot mint it.
