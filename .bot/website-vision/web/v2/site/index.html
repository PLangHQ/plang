A password is a lookup.

Signup forms, login pages, reset emails, session cookies. All of it exists to answer one question: which user.id is this?

Today

  1. Sign up with email and password
  2. Hash the password, store it
  3. Log in, compare hashes
  4. Create a session, set a cookie
  5. On every request: read the cookie, look up the session
  6. user.id = 4821

Then add password resets, 2FA, lockouts and breach notices.

With plang

Login
- select * from users where identity=%Identity%,
    write to %user%
- if %user% is empty then insert into user %Identity%,
    write to %user%
- return %user%

%Identity% is the caller, taken from the signature on the request. It arrives with every request, so there is nothing to log in to.

What goes away

  • Password tables
  • Hashing and salting
  • Login pages
  • Reset emails
  • Session cookies
  • Leaked password dumps
  • Credential stuffing
  • Phished passwords
  • API keys between apps

How plang works.

Natural language in. A deterministic, signed, sandboxed program out. This is everything in between.

  1. Start.goalSteps in plain language
  2. →
  3. plang buildLLM on llm.plang.is, build time only
  4. →
  5. .build/start.prPlain JSON: module, action, typed parameters
  6. →
  7. plang.NET runtime. No LLM.

A goal is a list of steps.

A goal is like a function. Steps run top to bottom. That's the whole grammar.

LlmSchema.test.goalfrom the test suite

Start
/ Query with JSON schema — verify response is parsed and dot-navigable
- [llm] system: 'You analyze sentiment. Respond in JSON only.'
    user: 'Analyze: I love sunny days'
    scheme: {sentiment:string, score:number}
    write to %result%
- assert %result% is not null
- assert %result.sentiment% is not null
Start
Goal name. Start is the entry point.
- step
One step per dash. Indented lines continue it.
%var%
Variables, with dot navigation into any value.
[llm]
Optional hint that names the module.
/ text
Comment. It is kept with the step.

Each step compiles to actions.

The builder maps every step to module actions with typed parameters. After that, the LLM is out of the loop.

Concepts

Identity

An identity is a key pair. The public key says who you are. The private key proves it. There are no passwords, no accounts and no server that holds them for you.

What an identity is

Each identity is an Ed25519 key pair with a name. It is created and stored on your own machine. The private key stays there unless you export it.

PropertyMeaning
nameThe identity's name, unique and case-insensitive
publicKeyEd25519 public key, base64
isDefaultWhether this is the identity plang uses by default
isArchivedArchived identities keep their keys but are hidden
createdWhen the identity was created

%MyIdentity%

The default identity is always available as %MyIdentity%. If none exists, plang creates one named default the first time you use it. In text, %MyIdentity% is the public key.

Start
- write out 'My name: %MyIdentity.Name%'
- write out 'My public key: %MyIdentity%'

Instead of passwords

When your app calls another plang app, the request is signed with your identity. On the receiving side, %Identity% is the caller: the public key from the signature. Login is a lookup:

Login
- select * from users where identity=%Identity%, write to %user%
- if %user% is empty then insert into user %Identity%, write to %user%
- return %user%

Nothing to log in to, no password to store and no API key to leak. %MyIdentity% is you. %Identity% is whoever is calling. How the signature itself works is in Signatures.

Actors

An app runs as three actors: User, Service and System. Each has its own identity and its own resources, so what the system does and what a user does are never the same signer.

Managing identities

StepWhat it does
create identity 'alice', set as defaultNew key pair, optionally the default
get identity 'alice', write to %id%One identity, or the default when no name is given
get identities, write to %all%All identities that are not archived
set default identity to 'alice'Switch the default
rename identity 'alice' to 'alice-prod'Keys are kept
archive identity 'alice'Hide it. The default can't be archived.
export identity 'alice', write to %x%Includes the private key. Keep it secret.

Example

Start
- create identity 'personal'
- create identity 'work', set as default
- write out 'Now using: %MyIdentity.Name%'
- set default identity to 'personal'
- write out 'Now using: %MyIdentity.Name%'

Concepts

Signatures

Everything plang sends carries a signature: proof of who sent it, and proof that it hasn't changed. You don't add it. It's already there.

What a signature is

A signature is a short value computed from the data and the sender's private key. Anyone who has the sender's public key can check it. If a single byte of the data changes, the check fails.

plang hashes the data with Keccak-256 and signs with Ed25519, using the sender's identity.

What gets signed

Every value in plang is Data. When Data leaves your app, over HTTP, through a channel or as a callback, it is signed on the way out if it isn't signed already.

  • The signature covers the name, type, value, properties and any signatures nested inside.
  • Forwarding keeps provenance. If Bob forwards Anna's signed message inside his own, both signatures travel and both can be checked.
  • Signing again is a no-op. Data that already carries a signature keeps it.

HTTP

Requests carry an X-Signature header by default, and signed responses are verified. To send a request without a signature, say so in the step.

- get https://api.example.com/orders, write to %orders%
- get https://httpbin.org/get, unsigned, write to %response%

What a signature contains

FieldPurpose
identityThe signer's public key
createdWhen it was signed
nonceA one-time value, so a captured message can't be replayed
hashKeccak-256 of the data
contractsWhat the signature is for, for example ['Payment', 'v1']. Default C0.
expiresOptional end of validity
headersOptional extra fields bound to the signature
signatureThe Ed25519 signature over all of the above

Verification

Callbacks are always verified before they run: a missing or altered signature is a hard error. Anywhere else you verify explicitly with verify. A check runs nine steps, and each failure has its own error key.

Error keyCause
NoSignatureThe data has no signature
InvalidTypeThe signature type is wrong
TimedOutOlder than the timeout (5 minutes by default)
ExpiredPast its explicit expiry
NonceReplayThis nonce was already seen
ContractMismatchContracts don't match what was expected
HeaderMismatchHeaders don't match what was expected
DataHashMismatchThe data was changed
SignatureInvalidThe cryptographic check failed

Sign and verify yourself

Start
- set %message% = 'Hello, signed world'
- sign %message%, write to %signed%
- verify %signed%, write to %isValid%
- write out 'Valid: %isValid%'

Bind a signature to a purpose and give it a short life:

- sign %payload% with contracts ['Payment', 'v1'], expires in 60000ms, write to %signed%
- verify %signed% with contracts ['Payment', 'v1'], write to %isValid%
